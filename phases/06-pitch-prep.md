# Phase 6 — Pitch Prep

**Goal:** prepare the narrative, not just the product. Judges remember the pitch; they only see
the product for a few minutes.

Hackathons don't all judge the same way — some want a live demo + slides, some want a timed
video submission, some want a written Devpost-style post with required sections, some score
against a published rubric. This phase does **not** assume one fixed pitch structure; it starts
by finding out this event's actual format and building the narrative to fit it.

## Steps

1. Gather this hackathon's actual submission/pitch requirements: format (live demo? recorded
   video? slide deck? written submission?), time or length limit, any required sections, and the
   published judging rubric if there is one. If this isn't known yet, that's the first thing to
   find out — don't guess the format.
2. Based on the actual format, propose a pitch structure that fits it. A live 3-minute demo and a
   written Devpost post need different structures; don't force the same template onto both.
3. Fill the structure in using material already produced: tie the problem section back to the
   Phase 1 framing, the solution section to the golden path from Phase 2, and draw on
   `decision-log.md` / `verification-log.md` for the "why we built it this way" substance.
4. If there's a live demo component, script it in the same click-order as the golden path —
   don't improvise under time pressure.
5. Anticipate 2–3 likely judge questions. For recruiting-linked events, explicitly prepare an
   honest answer to "how much of this did you build vs. generate, and what decisions were
   yours?" — this is exactly what `decision-log.md` and `problem-statement.md` are for.
6. Decide who presents/writes which part if it's a team.

## Decision point

> **The pitch structure itself** (once the actual format is known), **the final narrative, and
> who presents**, are the decision.

## Output

`pitch-script.md`:
- The submission format this was built for, and why the chosen structure fits it
- The narrative itself, in that structure
- Demo click-order script, if there's a live component
- Anticipated questions + answers, with references back to the decision log where relevant
